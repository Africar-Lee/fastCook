# 中餐食材匹配应用：产品与技术设计书

> **文档版本**：v0.1（需求梳理与技术交接）  
> **产品名称**：待定  
> **文档定位**：供产品设计、架构设计、数据工程与后续 LLM 协作使用。  
> **标记规则**：`[已确定]` 表示提出者已明确表达的产品意图；`[建议]` 表示可评审的设计方案；`[待决策]` 表示需要补充调研或选择的事项。

## 0. 执行摘要

开发一款**以中式家常菜为核心的、根据用户现有食材推荐已有菜谱的极简应用**。用户快速选择今天手头的食材，系统结合其长期保存的**调料柜**，从经过整理与验证的结构化中餐菜谱库中检索、判断可制作性并排序，清楚展示“能做什么”“缺什么”“为什么推荐”。

[已确定] 应用的核心价值来自**菜谱数据质量、食材语义归一化、可解释的匹配与排序，以及极简交互**。核心检索与推荐可独立运行。AI 的潜在用途包括辅助离线菜谱整理、推荐排序优化，以及用户主动启用的拍照食材识别。应用内不采用 AI 即时生成菜谱的产品思路。

[已确定] 可选 AI 功能可采用 **BYOK（Bring Your Own Key）**：用户自行配置模型服务商与 API Key，自主承担服务商费用，能够预览并审查提交给模型的请求、Prompt、图片及调用记录。应用需要尽可能降低运营方承担的模型费用，并以可验证的方式建立用户信任。

## 1. 产品定位与目标

### 1.1 核心问题

用户面对手头已有的食材，经常不知道能做哪些中式家常菜，尤其难以判断每一道菜还缺少哪些材料或调料。

### 1.2 核心用户流程

1. 用户首次进入应用，勾选家中常备的油、盐、酱油、醋、香料、酱料等，并保存至**持久化调料柜**。
2. 用户每次准备做饭时，快速选择手头可用的肉类、蔬菜、蛋、豆制品及主食等**当次食材**。
3. 系统合并两个来源的可用原料信息，并执行菜谱候选检索、约束判断和推荐排序。
4. 系统优先展示所需材料齐全的中餐菜谱，同时清晰说明其他菜谱缺少的关键材料、常用调料或可替代材料。
5. 用户点开具体菜谱，查看所需材料、参考用量、步骤、预计耗时及匹配依据。
6. 用户可随时维护调料柜，或重新选择当次食材。

### 1.3 产品衡量标准

- 从打开应用到找到**愿意制作且确实具备必要原料**的菜谱所需的时间。
- 前若干推荐的真实可制作比例；缺料提示的准确程度。
- 高频中式家常菜的覆盖率与菜谱可复现性。
- 用户每日完成输入食材与筛选结果所需的交互次数。
- 用户理解推荐原因和纠正错误匹配的容易程度。

## 2. 需求边界与优先级

### 2.1 核心能力 `[已确定]`

- 以**中式家常菜**为主要菜谱内容。
- 用户快速多选当前食材，选择变化后刷新匹配结果。
- 单独提供**长期保存的调料柜**，记录用户拥有的调味品与香料。
- 使用结构化、可追溯的现有菜谱数据进行匹配与推荐排序。
- 明确展示食材齐全程度、关键缺料、缺失调料、可适用的替代方案。
- 保持页面、操作和算法输出简洁；推荐结果应可解释。
- AI 能力保持可选；核心体验不依赖用户提供 API Key。

### 2.2 工程方案 `[建议，待评审]`

- 按“候选召回 → 可制作性约束判断 → 排序 → 解释生成”组织推荐管线。
- 优先使用确定性规则排序；积累可靠反馈数据后再考虑学习排序。
- 用标准原料 ID、别名表、分类层级、菜谱特定替代关系表达中餐食材语义。
- 以菜谱原始文本、规范化结构与审核结果分层管理数据。
- 用户当次食材的数量输入为可选项，界面明确区分“原料种类齐全”和“分量足够”。
- 食材历史组合可以快捷复用，减少重复选择。

### 2.3 可选增强能力 `[已确定的方向；细节待评审]`

- 用户通过 BYOK 启用视觉模型，对自己拍摄的食材照片进行识别。
- 识别结果转换为标准食材候选，交由用户确认，再进入同一套菜谱匹配管线。
- 如引入 AI 推荐排序，模型仅对已有候选菜谱做有限的重新排序或辅助判断，不创建不存在的菜谱。
- AI 请求具备显式触发、发送前预览、本地调用日志和密钥安全管理。

## 3. 物品模型：当次食材与持久化调料柜

### 3.1 两类用户维护的数据

| 对象 | 典型物品 | 保存方式 | 主要交互 |
|---|---|---|---|
| 当次食材 `current_ingredients` | 鸡蛋、番茄、土豆、猪肉、牛肉、青菜 | 面向本次烹饪的快速选择；可缓存上次组合 | 搜索、勾选、取消、快捷复用 |
| 调料柜 `pantry_condiments` | 盐、糖、生抽、老抽、蚝油、料酒、陈醋、花椒、八角、桂皮、干辣椒 | 持久化记录用户拥有的物品 | 首次配置、添加、标记用完、移除 |

[已确定] **储存位置与菜谱中的烹饪角色分开建模**：一个物品在用户端归入哪个存储区域，与它在特定菜谱中是主料、辅料、关键调味料还是可选配料，属于不同属性。例如姜蒜可以被家庭视为常备，也可能被视为本次购买的鲜食材。系统应支持合理的归属调整。

### 3.2 调料柜的建议行为

- 提供分类清单：基础调味、酱油与醋、酱料、油脂、干香料等。
- 以“是否拥有”为主要属性；允许设定“已用完”。精确余量输入并非核心交互前提。
- 每次匹配自动读取调料柜，不要求重复勾选。
- 在菜谱详情中区分：已拥有、缺少关键调料、缺少可选调料、存在适用替代方案。
- 保存采用设备安全可靠的持久化方案；跨设备同步方式另行决定。

### 3.3 食材语义

- `番茄`、`西红柿`：可规范化为同一食材实体。
- `猪肉`、`五花肉`、`猪里脊`：存在分类关系，不默认互相无条件替代。
- `生抽`、`老抽`：同属酱油类，但必须保留细分品种与不同用途。
- `香醋`、`米醋`、`陈醋`：是否可替代取决于具体菜谱做法。
- 可替代关系需包含使用场景、限制条件及对最终风味的影响。

## 4. 结构化菜谱数据模型

### 4.1 核心实体

1. `Dish`（菜品）：用户感知的一道菜，例如“番茄炒蛋”。
2. `Recipe`（具体做法）：该菜的一套可执行配方，包含份量、时间、步骤和版本来源。
3. `Ingredient`（原料）：有稳定 ID 的标准食材或调料实体。
4. `RecipeRequirement`（菜谱原料要求）：关联某个做法与原料，记录角色、必要性、用量、替代组等。
5. `IngredientAlias` / `IngredientRelation`：名称别名、种属、条件替代等关系。
6. `RecipeSource` / `ReviewRecord`：数据来源、许可、版本、整理人与审核记录。
7. `UserPantry` / `UserIngredientSelection`：用户长期调料与当次食材状态。

### 4.2 菜谱与做法的关系

同一道菜可能有多个经验证的做法。推荐列表可先按 `Dish` 去重聚合，再选取与用户现有物品**匹配最好的具体 `Recipe`**，从而减少几乎重复的菜谱占据推荐列表。

### 4.3 关键字段与含义

- `ingredient_id`：所有匹配计算使用的原料主键。
- `role`：例如 `main`（主料）、`secondary`（辅料）、`seasoning`（调味料）、`garnish`（点缀）。
- `importance`：菜谱特定的必要性，例如 `required`、`important`、`optional`。
- `quantity` / `unit`：原料参考数量与单位，可表达范围或“适量”，并记录置信度。
- `alternative_group`：表示“若干原料中满足某个条件即可”；具体替代规则与菜谱绑定。
- `equipment`、`prep_time`、`cook_time`、`servings`、`steps`：烹饪执行信息。
- `source`、`license`、`review_status`、`dataset_version`：数据治理字段。

## 5. 匹配与排序引擎

### 5.1 输入与输出

**输入**：当次食材标准 ID 集合、调料柜物品集合、可选数量、可选烹饪偏好。  
**输出**：去重后的菜品列表、每道菜选中的具体做法、匹配分层、缺料列表、替代提示、推荐原因。

### 5.2 推荐流水线 `[建议]`

1. **原料归一化**：处理别名、标准 ID、适用的层级匹配。
2. **候选检索**：利用原料—菜谱倒排关系筛出存在实质匹配的候选。
3. **约束判断**：检验各菜谱必需主料、关键调味要求、替代组与用户拥有情况。
4. **分层**：例如 `直接可制作`、`少量补充即可制作`、`缺少关键原料`。当未提供数量时，使用“种类齐全”而非保证分量充足。
5. **排序**：优先保证必要条件，再结合缺料成本、原料利用程度、做菜时间、口味或用户反馈排序。
6. **解释**：展示可制作依据、缺失原料，以及具体使用了哪项替代规则。
7. **同菜聚合**：同一道菜的不同做法合并展示，优先呈现匹配最佳的做法。

### 5.3 排序建议

使用**可解释的分层排序**作为起点，例如：

`可制作层级 > 缺失关键原料数量与权重 > 已有主料覆盖程度 > 烹饪时间 > 用户偏好`

必要性取决于具体做法。缺少豆瓣酱对某些川菜的影响显著；缺少鸡精对许多家常菜影响轻微。系统不能通过一个全局的“调料重要程度”表来决定所有菜谱的可制作性。

### 5.4 边界条件

- 用户只选择原料品种：只能判断**种类是否齐全**。
- 原料匹配成功但数量不明：不得向用户保证食材分量足够。
- 菜谱步骤提及原料而用料表缺失：标记数据异常，进入审核队列。
- 替代原料：需由明确的规则支持，不凭借通用类别自动放宽必要条件。
- 没有完全匹配的菜谱：展示缺料最少且可解释的候选。

## 6. 中文菜谱数据集建设

### 6.1 数据源策略

优先研究许可清晰、具有结构化潜力的中文菜谱数据。例如 `Anduin2017/HowToCook` 可作为候选基础数据源；可以参考中餐知识图谱或相关开源解析工具，吸收其建模方法。**正式使用前逐项核验仓库许可、菜谱内容、第三方插图和外链内容的授权边界。**

自行编写、验证的配方，以及获得明确授权的社区贡献可以逐渐形成自有数据资产。对第三方商业菜谱平台的文字与图片，应通过合法授权渠道获取。

### 6.2 采集与治理流水线

`Raw（原始菜谱） → Parsed（自动解析） → Normalized（原料标准化） → Reviewed（核验） → Published（版本发布）`

- 原始文本不可覆盖，应保留来源及抓取/导入时的快照与许可信息。
- 提取菜名、原料、份量、耗时、步骤、厨具。
- 将原料映射到规范 ID；发现新别名与新原料时进入词典审核。
- 标注主料、辅料、调料、必需性及适用的替代条件。
- 对原料表与烹饪步骤执行一致性检查，并识别重复或高度相似的做法。
- AI 可作为**离线数据整理助手**提出结构化结果与标注建议；人工或高可信规则审核关键关系。
- 每条菜谱支持追溯到原始资料、审核记录与数据版本。

### 6.3 质量指标与测试集

- 高频中餐覆盖率。
- 食材/调料列表与步骤的一致性。
- 规范名称映射正确率。
- 关键调料必要性与替代规则准确率。
- `Feasibility Precision@K`：前 K 个标为可制作的推荐中，实际符合已声明条件的比例。
- 缺料清单准确率。
- 菜谱可复现性与步骤完整性。

[建议] 建立**人工标注的厨房库存黄金测试集**：覆盖常见菜品、不同调料柜配置、别名、缺料、替代品及数量不确定场景。每次发布数据集或修改推荐逻辑均进行回归测试。

### 6.4 数据建设起点 `[建议，不构成硬性规模要求]`

可考虑先人工验证约 300—500 道常见中式家常菜，整理数百种标准原料与常见调料。在覆盖率和准确性得到证据之前，避免单纯追求大规模数据量。

## 7. 界面与交互约束

### 7.1 主要页面

- **今日食材**：高频食材快捷勾选、搜索、分类、最近使用组合。
- **推荐结果**：默认优先展示原料齐全的菜品，显示缺料数量、关键缺料、耗时和简短推荐依据。
- **菜谱详情**：原料要求、调料匹配、做法、份量、耗时、具体缺料与替代条件。
- **我的调料柜**：分类勾选与持久化维护。
- **设置**：数据偏好、可选 BYOK 配置、安全与审查选项。

### 7.2 交互原则

- 以点击、勾选、筛选为主，尽量减少自然语言输入。
- 用户能够在极少操作内从选择食材到查看菜谱。
- 结果即时、可解释，关键缺料一目了然。
- 调料柜在首次设置后以低频维护为主。
- 识别错误或匹配错误应有直接的修改入口。

## 8. 可选 BYOK 视觉食材识别

### 8.1 目标 `[已确定]`

允许用户自行配置视觉能力模型的 API Key，主动拍照识别已有食材，从而减少手动勾选。AI 识别结果进入既有菜谱数据库和规则匹配系统。应用运营方尽可能不承担模型调用成本。

### 8.2 推荐流程 `[建议]`

`拍照/选图 → 本地预处理 → 查看请求详情并授权 → 视觉模型识别 → 解析结构化食材 → 用户确认/修正 → 标准原料映射 → 常规菜谱匹配`

- 尽量缩小图片尺寸，并清理 EXIF 等不必要的元数据。
- 仅发送识别任务所需的图片与指令；调料柜及用户历史无需随识别请求发送。
- 模型输出食材名称、可选数量估计、不确定性标记；前端允许更正。
- 对没有明确识别的对象，不自动推定其一定存在。
- 具体模型需支持图片输入；API 兼容性与费用由适配器处理。

### 8.3 可审查的调用机制 `[已确定的设计原则]`

**发送前**：向用户展示服务商、真实请求目标、模型、实际 Prompt 与参数、待上传图片/附件、可能发送的数据范围，以及费用预估（如可计算）。用户主动确认请求。  
**发送后**：用户可检查本地调用日志，包括请求时间、任务类型、模型、脱敏请求内容、响应摘要、实际用量和费用信息（如服务商提供）。  
**可验证性**：将调用逻辑集中在独立、便于审计的模块；提供可检查的源码与网络访问说明。界面声明必须和实际网络行为一致。

- 不记录明文密钥到日志、分析事件或崩溃报告。
- 请求预览应反映**实际发送内容**；若图片转换为缩略图、Base64 或文件上传，应标明处理方式并提供可核对的信息。
- API Key 可随时删除；请求日志支持清除。
- 提供调用上限、费用提示，并引导用户在模型供应商控制台设置预算/额度限制。
- 直接从移动客户端使用用户密钥存在安全风险，需通过系统安全凭据存储及供应商政策评估；网页和小程序还受跨域、域名限制及密钥暴露面影响。
- 如需部署中转服务，必须明确它可接触到的请求、图片与凭据范围，提供用户可理解的信任边界。推荐优先评估无需让运营方接触密钥或原图的技术路径。

### 8.4 AI 在推荐排序中的位置

若采用 AI 辅助排序，应先由确定性引擎生成**已经存在于数据库中的候选菜谱**，再将最小必要特征提交给模型，要求仅返回候选菜谱 ID 的排列或说明。模型输出须校验 ID 合法性，展示排序依据，并允许恢复基础排序。

## 9. 技术架构建议（供进一步评审）

概念上可拆分为：

1. **客户端**：食材与调料选择、用户偏好、菜谱浏览、可选拍照与 BYOK 审查。
2. **菜谱数据层**：标准原料字典、结构化菜谱、别名及替代关系、审核与版本信息。
3. **匹配引擎**：候选召回、必要条件检查、排序、结果解释。
4. **数据处理流水线**：授权导入、解析、归一化、审核、打包发布。
5. **可选模型适配层**：供应商适配、请求审查、凭据读取、用量统计、结构化响应验证。

数据库可评估 PostgreSQL；客户端可评估微信小程序与跨平台移动技术，具体选型需与 BYOK 直连、安全与维护成本共同评估。对小规模结构化数据，可研究设备端匹配与数据打包方案以降低服务端运营成本。技术栈**尚未最终确定**。

### 9.1 非功能性要求

- 推荐可解释、结果稳定、能够回归测试。
- 低交互成本、合理响应速度、适合移动端。
- 用户调料柜、个人偏好与 API Key 具有明确的数据生命周期。
- 处理食材照片时遵循最小数据传输原则。
- 数据集有来源记录、质量状态和版本管理。
- 算法与数据的调整可审计、可复现。
- 尽可能控制模型调用费用和长期维护成本。

## 10. 示例验收场景

| 场景 | 期望行为 |
|---|---|
| 用户选择“番茄、鸡蛋”，调料柜有油、盐 | 推荐可制作的番茄炒蛋做法，并列出具体条件 |
| 用户选择“青椒、猪肉”，调料柜有生抽但没有蚝油 | 根据具体做法的必要性展示可行做法或缺料说明 |
| 用户仅有牛肉，某菜要求猪里脊 | 不自动判定为原料齐全 |
| 用户选择“西红柿”，数据库要求“番茄” | 通过别名归一化正确匹配 |
| 用户有米醋，菜谱要求香醋 | 只有在该做法存在适用替代规则时才视为可替代 |
| 用户缺少豆瓣酱，菜谱高度依赖豆瓣酱 | 显示关键调料缺失，并降低可制作层级 |
| 用户没有输入克数 | 界面仅声明原料种类齐全，不保证分量充足 |
| 用户删除 BYOK API Key | 凭据从应用管理的安全存储中清除，相关功能停止调用该密钥 |
| 用户发起拍照识别 | 发送前可查看模型、请求目标、Prompt、图片和请求参数 |
| 识别结果将土豆误判成红薯 | 用户能在进行菜谱匹配前快速修正 |
| 关闭或未配置 AI 功能 | 用户仍可完成手动选材与菜谱推荐全过程 |

## 11. 项目主要风险与工程难点

1. **数据版权与授权**：开源代码的许可不必然覆盖第三方文字与图片；应记录逐项可用范围。
2. **中餐非标准化**：菜名相同但做法、配料及调料各异，应区分菜品与具体做法。
3. **食材语义复杂**：同义、细分类别、烹饪功能与条件替代不能仅靠字符串匹配。
4. **可制作性误报**：推荐为“能做”却缺少关键原料会直接损害信任。
5. **调料必要性主观差异**：应以具体菜谱做法与经过验证的标注为依据。
6. **用户输入负担**：临时食材选择应轻量，调料柜应长期保存并便于维护。
7. **BYOK 密钥与隐私**：客户端密钥储存、请求审计、图片上传和中转信任边界需要安全设计。
8. **产品复杂度**：持续检验每项功能是否提升“快速找到能做的菜”的核心体验。

## 13. 交给下一位 LLM 的工作指令

请以本文作为产品需求的主要依据，按如下顺序推进：

1. **先复核需求并识别关键不确定性**。将已确定原则与建议方案分开，不自行加入 AI 生成菜谱或复杂社交功能。
2. **设计可执行的菜谱数据标准**：表结构/JSON Schema、主料与调料的必要性、食材别名与层级关系、条件替代、数据溯源。
3. **给出可解释的菜谱匹配与排序算法**：输入输出、分层判定、去重、索引策略、边界条件、复杂度及测试案例。
4. **制定可落地的数据集建设方案**：候选数据源许可核验、导入清洗、归一化、抽检、黄金测试集和质量指标。
5. **提供极简用户交互设计**：当次食材、持久化调料柜、推荐列表、菜谱详情及低成本纠错。
6. **评估 BYOK 模块的安全与透明性**：用户主动授权、请求完整预览、日志脱敏、密钥管理、服务商兼容和客户端/中转架构的取舍。
7. **输出可分工实施的工程任务清单与验收标准**，明确哪些方案已得到需求支持，哪些仍须用户作决定。

**评判方案的首要准则：** 能否以最少交互、可靠数据和可解释算法，让用户快速找到真正能够制作的中式家常菜；同时控制维护与模型调用成本。
