# 菜谱数据标注与校验规范

阶段 1 使用结构化草稿检验数据约定。目录包含 20 道菜、58 个原料词条、3 条替代规则和一套调料柜模板。全部内容标记为 `pending_review`，来源记录为 AI 辅助编辑草稿，许可状态为 `pending`，审核记录为空。

人工审核需要确认原料身份、用量、步骤、必要性和替代效果。工具检查结构与引用一致性；“已试做”需要对应的实际烹饪记录。确定性排序和 AI 仅辅助离线整理的边界已经确认。

## 文件组织

| 位置 | 内容与编辑方式 |
|---|---|
| `data/catalog.meta.json` | 数据版本、结构版本、状态与默认语言 |
| `data/ingredients/core.json` | 标准原料数组，使用稳定 ID |
| `data/dishes.json` | 菜品名称与 ID，多个做法可以共用一个菜品 |
| `data/recipes/*.json` | 每个文件一个完整 Recipe |
| `data/rules/substitutions.json` | 全局和菜谱级替代规则 |
| `data/templates/cn_basic.json` | 模板数组，省去已经隐含的油、盐和水 |
| `data/sources.json` | 来源、版本和许可记录 |
| `data/reviews.json` | 与内容及依赖哈希绑定的审核记录 |
| `data/schemas/catalog.schema.json` | 完整 Schema 的唯一维护入口 |

四个实体入口为 [Ingredient](../data/schemas/ingredient.schema.json)、[Recipe](../data/schemas/recipe.schema.json)、[SubstitutionRule](../data/schemas/substitution-rule.schema.json) 和 [PantryTemplate](../data/schemas/pantry-template.schema.json)。它们引用完整 Schema 的 `$defs`，使用验证器时先注册 [catalog.schema.json](../data/schemas/catalog.schema.json)。原 `docs/design/catalog.schema.json` 保留为兼容引用入口。

新增做法时使用一个新文件，确认 `dish_id` 已存在。给已有菜增加变体时保留相同 `dish_id`，分配新的 `recipe_id`。修改内容后保持待审核，直到新的内容和依赖获得对应的审核记录。

## 原料名称与层级

`names` 存放标准名，`aliases` 存放搜索词。番茄的“西红柿”可自动归一。猪里脊和牛里脊共用“里脊肉”搜索词时，两者都要标为 `needs_confirmation`。将其中任何一项设为 automatic 会被校验器拒绝。

`taxonomy_parent_id` 用于分类浏览，`matching_parent_ids` 表达经审核的具体原料满足泛指需求。例如猪里脊可以指向泛指猪肉。菜谱确实接受任意适用猪肉部位时才使用 `pork`；糖醋里脊使用 `pork_tenderloin`。牛肉和猪肉即使同属肉类，也不产生满足关系。

鲜香菇与干香菇分开，生抽与老抽分开，熟米饭保持独立词条。形态和处理方式会影响做法时，应明确建模，避免用别名隐藏差异。

字典图必须无环，原料引用必须存在。`selectable=false` 的导航节点不能加入调料柜模板。油、盐、水的隐含常备标记用于本批结构样例，用户是否能明确声明缺少仍属于交互决策。

## 必要性与占用性

| 字段值 | 判定方法 | 正例 | 不应采用的标注 |
|---|---|---|---|
| required | 缺少后不能完成该做法或无法保持菜品身份 | 番茄炒蛋中的鸡蛋 | 将主料设 optional，仅为了提高匹配数量 |
| important | 有完整省略方法，但风味明显改变 | 某一青椒炒肉做法中的蚝油 | 没有可执行省略方法却标为 important |
| optional | 有完整省略方法，影响轻微 | 炒饭收尾的葱花 | 把所有 seasoning 一律标为 optional |
| consumes=true | 按种类管理库存时，应保守确认是否用完 | 蒜蓉西兰花中大量使用的蒜 | 仅依据 main 或 seasoning 自动赋值 |
| consumes=false | 默认不占用整种库存 | 炒菜中的少量盐 | 认为 false 表示完全不消耗或保证余量充足 |

`role` 用于展示分组，`importance` 用于必要性，`consumes` 用于库存占用。蒜可以同时为 seasoning、required、consumes=true。食材存放于调料柜还是当次清单，由用户数据决定。

每个 important 或 optional 项必须有 `omission.note` 和 `omission.step_changes`。省略葱花时可以跳过只负责加葱的步骤。关火、装盘或检查熟度等收尾动作放在独立保留步骤中，避免随点缀一起被删掉。

步骤必须引用所使用的 `requirement_id`，每项需求至少被一个步骤使用。修改步骤需要同步更新引用。可省略项尽量各有独立步骤，减少多个变更同时作用于同一步的冲突。

空 `step_changes` 仅适用于原文已经明确条件化的用料操作，其正确性仍需人工审核。工具不会从“可加”“按喜好”等自然语言自动推断执行逻辑。

## 用量与做法

确定量用 `value + unit`，范围用 `min + max + unit`，适量用 `unit=to_taste`。数值必须为正，区间下限不得超过上限。克和毫升优先；piece 可以是分数。记录 tbsp 或 tsp 时，必须同时声明 `spoon_standard=metric_15ml_5ml`。

原始材料中的“半碗”应保留在待处理原文，核实容积后再归一化。解析失败不能改成“适量”。同一用料被多次使用时，在步骤中写明分配，例如总淀粉 65 克，其中 60 克裹浆、5 克勾芡；人工审核确认分配之和与用料表一致。

步骤、厨具和总时长按同一个具体做法记录。若某个可省略步骤需要额外厨具，应检查省略后是否仍会被该厨具要求阻挡。此类条件复杂时拆成独立做法，保持每个 Recipe 的必要条件清晰。

菜单的 meat 和 veg 用于荤素筛选。含猪肉的麻婆豆腐草稿归 meat。菜谱含有可省略肉类时，仍按完整做法分类；素食做法需要独立记录，不能只根据菜名判断。

## 替代规则

`required_ingredient_id` 为菜谱目标，`substitute_ingredient_id` 为用户实际拥有的替代品。规则有方向，单次最多应用一条替代边。两条规则连成路径不产生第三条替代关系。

| 等级 | 标注要求 |
|---|---|
| equivalent | 经过审核后可确认对该用途近乎无差异，详情仍记录替代 |
| acceptable | 能按已调整的做法完成，明确写出风味或口感变化 |
| poor | 影响明显，默认不启用，必须有对应做法的显式 allow |

米醋替香醋样例限定炒制方法，使用相同毫升量作为待核验的示例比例。土豆丝用于演示全局规则；醋溜白菜的相同需求显式 forbid 该替代。这个样例展示规则结构，替代比例和效果仍需要试做确认。

菜谱级规则设置 `scope=recipe` 和 `recipe_id`，并由对应需求的 allow 激活。宫保鸡丁示例允许同重量去骨去皮鸡腿肉替鸡胸肉；糖醋里脊示例允许土豆淀粉替玉米淀粉，并明确覆盖裹浆与勾芡两种用途。它们均保持待审核。

同一需求和有向原料对的重复或矛盾覆盖会被工具拒绝，防止用不同 rule_id 绕过 forbid。替代条件只能引用做法中已经列明的配料；需要新增配料时建立另一做法。

`quantity_ratio` 必须适用于原需求单位。缺少比例或单位不适用时，必须有可执行的用量说明并设置 `requires_confirmation=true`。说明是否充分由人工审核。修改操作流程时使用 `recipe_step_changes_required`，在 allow 中列出具体步骤变更。

## 来源与审核

每个正式来源应记录原文定位、固定版本和快照哈希，许可证据独立保存。正文和图片分别审查。`Source` 的字段位置包括 `provenance`、`revision` 和 `license`；获取时间、采用范围与转换记录放入导入清单。

这批样本统一使用 `stage1_editorial_draft` 来源，准确记录 AI 辅助整理，没有借用 HowToCook 等上游名义。权利和烹饪资料尚未核验，所有记录继续保留草稿状态。

审核记录使用 `subject_type`、`subject_id`、`subject_sha256` 和 `dependency_sha256`。实体及其依赖经 RFC 8785 规范化后计算 SHA-256，依赖按对象类型与 ID 排序，排除审核记录本身。`reviewFingerprint` 可以计算对应摘要，不会创建通过记录。

发布检查采用保守的工程检查规则。所有实体需要 structural 审核；原料、菜品、模板、菜谱和替代规则需要 semantic 审核；菜谱和替代规则还需要 cooking 审核；来源需要 license 审核。相同内容与依赖下，以最新时间的记录决定结果，同时存在拒绝记录时不通过。具体发布政策仍需维护者确认。

受控许可证据包和上游快照的实体验证尚未接入。来源即使声明 verified，发布检查也会返回 `release.evidence_unverified`。因此发布检查提供拦截能力，完成证据包验证之前不会批准发布。工具不会根据来源字段自动读取任意本地文件或发起网络请求。

## 本地校验

数据工具使用 Node.js 22 及以上版本。执行 `npm ci` 安装锁定的开发依赖后运行以下命令。

```sh
npm run data:validate
npm test
npm run data:check-release
```

普通校验检查数据结构、ID、外键、原料图、别名冲突、语言回退、用量区间、步骤和替代绑定。测试覆盖正常与错误路径。发布检查对本批草稿返回非零退出码是预期结果；把根状态改为 release_candidate 或 published 也会自动触发同样的发布检查。

文件读取只接受 data 目录中的普通 JSON 文件，单文件上限 1 MiB，总量上限 16 MiB。文件按名称排序后组合，保证读取顺序稳定。超限、语法错误和越界链接会返回带路径的错误。

Schema 使用 Ajv 的 Draft 2020-12 验证器，日期格式由 ajv-formats 验证；审核摘要由 canonicalize 提供规范化序列化。[Ajv Schema 支持](https://ajv.js.org/json-schema.html)、[格式校验](https://ajv.js.org/guide/formats.html)、[canonicalize](https://github.com/erdtman/canonicalize)

工具可以发现步骤引用残留，仍需人工阅读自然语言中的配料、数量和操作。结构检查通过、数据审核通过与实际试做通过分别记录。
