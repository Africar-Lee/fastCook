### v0.1 → v0.2 主要变更

1. 明确平台为**移动端 App**，项目以**开源**方式开发，目标用户为全球用户，早期聚焦中国大陆。分发只通过 **GitHub 源码与 APK Release**，不上架应用商店。
2. 新增**版本范围与“不做”清单**，BYOK 拍照识别移至 v2，**删除 AI 辅助排序**。
3. 新增**“一顿饭”配餐能力**，与“一道菜”并存，通过菜篮渐进出现，不设模式开关。
4. 调料柜改为**模板减法初始化**；引入**隐含常备项**；当次食材**默认继承上次选择**。
5. 匹配结果由“有/没有”二态改为**有/没有/不确定**三态；明确**层级匹配方向规则**。
6. 替代规则改为**全局默认 + 菜谱级覆盖**两层结构，控制标注成本。
7. 新增**“再买一样能解锁几道菜”**反向推荐与快捷筛选标签。
8. 确定**设备端匹配、无业务后端**的架构方向；菜谱数据随 APK 版本更新，不设独立的数据下载通道。
9. 新增**开源策略**（代码/数据许可、贡献流程、CI 质量门禁、网络行为声明）与**国际化数据设计**。
10. 衡量标准补充可检验的目标值；修正版本号不一致问题。
11. 技术栈确定为 **Expo（React Native + TypeScript）**；界面采用 **Material Design 3**。
12. App 申请网络权限，为后续**社区菜谱分享**预留（v1–v1.5 不发起网络请求）；新增 2.5 节分享功能的设计原则。
13. 不使用动态取色；品牌色为**柔和的黄色**，浅色模式为黄白搭配，黄色仅用于关键按钮。
14. 确定**标志与 App 图标**：方向 C2「三点入锅」（见 9.4）。

## 0. 执行摘要

开发一款**开源的、以中式家常菜为核心的、根据用户现有食材推荐已有菜谱的极简移动应用**。用户快速确认手头的食材，系统结合长期保存的**调料柜**，从经过整理与验证的结构化菜谱库中判断可制作性并排序，清楚展示“能做什么”“缺什么”“为什么推荐”。用户既可以只找**一道菜**，也可以把几道菜组合成**一顿饭**。

[已确定] 核心价值来自**菜谱数据质量、食材语义归一化、可解释的匹配与排序、极简交互**。核心功能完全离线、无需账号、不依赖任何 AI 服务。应用内不采用 AI 即时生成菜谱。

[已确定] 可选的拍照识别食材采用 **BYOK（Bring Your Own Key）**：用户自行配置模型服务商与 API Key，请求由设备直连服务商，用户可在发送前完整预览请求内容。项目运营方不承担模型费用，也不接触密钥与图片。

[建议] 由于项目开源，应用的全部网络行为可以被源码审计，这是建立用户信任的核心手段。

## 1. 产品定位

### 1.1 核心问题

用户面对手头已有的食材，经常不知道能做哪些中式家常菜，难以判断每道菜还缺什么；需要做一顿饭时，还要考虑荤素搭配、食材够不够分、灶台怎么安排。

### 1.2 目标用户

[已确定] 长期目标为全球用户；早期内容与交互针对中国大陆的家庭烹饪者。

[建议] 早期优先服务以下画像，用于设定默认值与菜谱难度：

| 画像 | 典型诉求 | 对设计的影响 |
|---|---|---|
| 独居/上班族 | 下班后 15–30 分钟做一道菜 | 单菜推荐为默认；耗时筛选突出 |
| 家庭做饭者 | 一荤一素一汤，照顾多人 | 配餐功能、人数设置、灶具并行 |
| 烹饪新手 | 不确定缺了某样调料还能不能做 | 缺料影响说明、替代说明清晰 |
| 海外华人（后期） | 当地买不到部分中式食材 | 替代规则、地区可得性标签 |

### 1.3 两种使用场景 `[已确定]`

- **找一道菜**：用户只想知道现在能做哪道菜。这是默认路径。
- **配一顿饭**：用户需要组合多道菜，要求搭配合理、主料不冲突、可以安排制作顺序。

两种场景共享同一套匹配引擎和结果页；“一顿饭”通过菜篮渐进出现，不设置模式开关（见第 8 节）。

### 1.4 差异化定位 `[建议]`

现有的“今天吃什么”类工具多为随机推荐或简单关键词匹配。本项目的差异在于：

1. **持久化调料柜**：用户不需要每次声明调料。
2. **可制作性判断**：区分“能做”“能做但有影响”“差一样”，并解释原因。
3. **条件替代与层级语义**：不靠字符串匹配，也不随意放宽条件。
4. **开源、核心功能离线、可审计**：核心功能无需账号、无追踪、BYOK 直连。

### 1.5 衡量标准与目标值 `[建议，待用户测试校准]`

| 指标 | 目标值 |
|---|---|
| 老用户从打开到看到可做菜谱 | 中位数 ≤ 15 秒；继承上次食材时 0 次点击 |
| 新用户完成调料柜初始化 | ≤ 60 秒 |
| 黄金测试集上“能做”层的 Feasibility Precision@5 | ≥ 95% |
| 缺料清单准确率 | ≥ 95% |
| 高频家常菜清单覆盖率（v1 发布时） | ≥ 80%（清单见第 10.2 节） |
| 配餐建议主料冲突率（未声明“够用”时） | 0 |

## 2. 版本范围

### 2.1 v1（MVP）`[建议]`

- 手动选择当次食材：高频宫格、分类、搜索（含拼音首字母）。
- 调料柜：模板减法初始化、隐含常备项、本地持久化。
- 单菜推荐：三层结果、缺料与替代说明、快捷筛选标签。
- “再买一样能解锁几道菜”提示。
- 菜谱详情：原料匹配状态、用量、步骤、耗时。
- “做了这道”：一键从当次食材中移除已用掉的主料。
- 约 200–300 道人工核验的中式家常菜；数据随安装包附带，完全离线。
- 数据层预留 `course`、`equipment_slots`、`consumes` 字段（为 v1.5 配餐准备，v1 即标注）。

### 2.2 v1.5

- 菜篮与手动配餐；“帮我配一顿”自动配餐。
- 人数设置与顿饭规模默认规则。
- 本地备份导出/导入。

### 2.3 v2

- BYOK 视觉识别食材。
- 一顿饭的制作顺序编排（按耗时与灶具自动排程）。
- 多语言界面与首批非中文内容；地区可得性与地区调料柜模板。
- 用户自建/私有菜谱（仅本地），使用与正式菜谱相同的结构化编辑器。
- 菜谱导出/导入（文件、二维码），为社区分享做准备（见 2.5）。

### 2.4 不做 `[已确定/建议]`

- **不做** AI 生成菜谱。`[已确定]`
- **不做** AI 辅助排序：候选集规模小，确定性分层排序已足够，AI 排序带来的复杂度和信任成本高于其收益。`[建议]`
- **暂不做** 评论、点赞、关注等社交功能。菜谱分享与上传是后续规划（见 2.5）。
- **不做** 营养计算、减脂计划、电商导购、广告。
- **不做** 账号体系（v1–v2 期间）；不收集分析数据。

### 2.5 后续规划：社区菜谱分享 `[已确定方向；实现方案待决策]`

用户将来可以方便地上传和分享自己的菜谱。为此 App 从 v1 起即申请网络权限（v1–v1.5 实际不发起网络请求，见 3.4）。

设计原则 `[建议]`：

1. **先结构化，再分享**：上传的菜谱必须用 App 内的菜谱编辑器创建。原料从标准原料字典中选择（字典中没有的走“建议新增”），`importance`、`consumes` 等字段与正式菜谱一致，否则无法参与匹配。v2 的“本地私有菜谱”就是这个编辑器的第一个用途。
2. **社区菜谱与核验菜谱分开**：社区菜谱带“社区”标识，可在设置中隐藏；不计入 Feasibility Precision 等质量指标；层级判定照常进行，但界面提示该菜谱未经核验。优质社区菜谱经审核后可以合入核验菜谱库，回到开源仓库的数据流程。
3. **许可在上传时明确**：上传即同意以项目数据许可（建议 CC0）发布，界面中清楚说明。
4. **隐私最小化**：上传内容不附带调料柜、食材记录等任何个人数据。是否需要账号、需要什么程度的身份，随实现方案决定。
5. **分步实现**：
   - **第一步**：菜谱导出为文件或二维码，通过任意聊天工具分享，对方导入。零服务端成本，也能验证用户是否真有分享需求。二维码容量有限，较长的菜谱需压缩或改用文件。
   - **第二步**：再决定中心化方案，例如自建轻量服务，或以 GitHub 仓库作为存储由 App 生成提交。需要评估服务器成本、内容审核、防滥用与维护负担。

## 3. 开源策略

### 3.1 许可 `[建议，待决策]`

| 对象 | 建议许可 | 理由 |
|---|---|---|
| 应用代码 | Apache-2.0、MIT 或 GPL-3.0 | 仅通过 GitHub 分发 APK，不受应用商店条款限制，三者均可。宽松许可（Apache-2.0 含专利授权条款）便于他人二次开发；GPL-3.0 保证衍生版本继续开源。注意：若将来上架 App Store，GPL 系许可与其分发条款存在已知冲突 |
| 菜谱与食材数据 | CC0 1.0（或 CC BY 4.0） | 上游 HowToCook 为 Unlicense，CC0 保持同等开放度，最大化复用；若希望要求署名可选 CC BY 4.0 |
| 图片与插图 | 逐项记录来源与许可 | 不与数据许可混同 |

贡献者通过 DCO（`Signed-off-by`）声明有权以上述许可贡献内容。`[建议]`

### 3.2 仓库结构 `[建议]`

早期采用单仓库（monorepo），便于统一版本：

```
/app          移动端应用代码（Expo）
/packages
  /engine       匹配与配餐引擎（纯 TypeScript，App 与数据工具共用）
/data
  /ingredients  标准原料字典（每类一个文件）
  /recipes      每个做法一个 YAML/JSON 文件
  /rules        全局替代规则
  /templates    调料柜模板
  /golden       黄金测试集
/tools        导入、解析、校验、打包脚本
/docs         设计文档、数据规范、贡献指南
```

### 3.3 CI 质量门禁 `[建议]`

每个涉及 `/data` 的 Pull Request 必须通过：

1. JSON Schema 校验。
2. 引用完整性：所有 `ingredient_id`、`dish_id`、替代规则引用的 ID 均存在。
3. 步骤—用料一致性检查：步骤中出现的原料名必须在用料表中（基于别名词典的启发式检查，告警需人工确认）。
4. 黄金测试集回归：匹配结果与期望不一致则失败。
5. 数据包构建成功，体积变化在阈值内。

### 3.4 网络行为声明 `[建议]`

App 从 v1 起申请网络权限，为 BYOK 与社区分享预留。菜谱数据随 APK 一同发布，应用本身不下载数据。各版本的实际网络行为：

| 版本 | 网络请求 |
|---|---|
| v1–v1.5 | 无 |
| v2 | BYOK 模型调用，仅在用户确认后直连用户配置的服务商 |
| 社区分享上线后 | 浏览、上传、下载社区菜谱，仅在用户使用该功能时发生 |

约束：

- **所有网络请求必须经由统一的网络模块**，代码审查中禁止在其他位置直接发起请求，便于审计。
- 每个联网功能在设置页与 README 中逐项列出：请求目标、发送内容、触发时机。新增联网功能时必须同步更新该清单。
- 核心功能（选材、匹配、配餐、菜谱浏览）在断网时完全可用。无分析、无崩溃上报（如未来引入，必须默认关闭并明确告知）。用户反馈通过“报告问题”生成预填的 GitHub Issue 链接或导出一份 JSON，由用户自行决定是否提交。

### 3.5 开源可持续性

- 数据审核是主要瓶颈：维护者需要定义清晰的审核清单，并鼓励“小 PR、单道菜”贡献。
- 黄金测试集本身也接受贡献，用于防止回归。
- 贡献指南需包含：如何新增菜谱、如何新增原料与别名、如何标注必要性与替代规则、示例。

## 4. 物品模型：当次食材与调料柜

### 4.1 两类用户数据

| 对象 | 典型物品 | 保存方式 | 主要交互 |
|---|---|---|---|
| 当次食材 `current_ingredients` | 鸡蛋、番茄、土豆、猪肉、青菜 | 本地持久化，**默认继承上次选择** | 勾选、取消、清空、“做了这道”后自动扣减 |
| 调料柜 `pantry` | 生抽、老抽、蚝油、料酒、陈醋、花椒、八角、干辣椒 | 本地持久化 | 模板初始化、标记用完、添加、移除 |

[已确定] **储存位置与菜谱中的烹饪角色分开建模**。葱姜蒜等物品可由用户自行决定放在调料柜（视为常备）还是当次食材。

### 4.2 调料柜：模板减法初始化 `[建议]`

- 首次进入时提供一套预设模板（v1：“中国家常基础”），默认全部勾选，用户只需取消没有的。
- 模板示例：食用油、盐、白糖、生抽、老抽、醋、料酒、蚝油、淀粉、葱、姜、蒜、干辣椒、花椒、八角。最终清单需根据第 10 节的高频菜谱数据统计确定。
- 提供“更多调料”分类列表用于追加：酱油与醋、酱料、油脂、干香料等。
- 以“有/没有”为唯一属性；“已用完”即取消勾选。不记录余量。
- 后期按地区提供不同模板（如“海外华人厨房”）。

### 4.3 隐含常备项 `[建议]`

**水、食用油、盐**被视为隐含常备：

- 不在调料柜中要求用户声明。
- 不出现在任何“缺料”提示中，以免每道菜都附带无信息量的提示。
- 在菜谱详情的用料表中正常显示用量。
- 隐含常备项列表在原料字典中以 `implicit_staple: true` 标记，可通过数据更新调整。

### 4.4 当次食材：继承与扣减 `[建议]`

- 打开应用时显示上次的选择，顶部提示“上次的食材还在吗？”，提供**清空**入口。
- 用户在菜谱详情点击“**做了这道**”后，弹出该菜 `consumes: true` 的主料，默认全部勾选移除，用户可取消勾选保留（例如鸡蛋还有剩）。
- 不做自动过期，避免系统误删用户实际拥有的物品。

### 4.5 食材语义：层级方向规则 `[建议]`

原料字典中每个原料可以有一个父类，例如 `猪里脊 → 猪肉 → 肉类`。

匹配时采用**方向规则**：

| 用户拥有 | 菜谱要求 | 判定 |
|---|---|---|
| 猪里脊 | 猪里脊 | **有** |
| 猪里脊 | 猪肉（任意部位） | **有**（具体满足泛指） |
| 猪肉（未指明部位） | 猪里脊 | **不确定**（需确认部位） |
| 牛肉 | 猪里脊 | **没有**（兄弟类不互相满足，除非存在替代规则） |
| 番茄 / 西红柿 | 番茄 | **有**（别名归一化） |

菜谱需求应尽量写在合适的抽象层级，例如“绿叶菜（任意）”“猪肉（任意部位）”，以减少替代规则数量。

## 5. 国际化与地区化 `[建议]`

[已确定] 目标用户为全球用户，因此数据结构从 v1 起支持多语言，即使 v1 只提供简体中文内容。

- **原料 ID 与语言无关**：使用英文 snake_case 标识（如 `pork_tenderloin`），名称与别名按 locale 存储。
- **搜索索引按语言构建**：中文提供拼音全拼与首字母索引；其他语言后续扩展。
- **菜谱文本按 locale 存储**：菜名、变体名、步骤均为 `{locale: text}` 结构；缺失翻译时回退到原始语言并标注。
- **单位**：数据统一存储为公制与语言无关的单位代码（`g`、`ml`、`piece`、`tbsp`、`tsp`、`to_taste`），展示层按 locale 转换。
- **地区可得性**（v2）：原料可标注地区可得性标签，配合替代规则为海外用户提示“当地可用的替代品”。
- **界面文案**：v1 即使用 i18n 框架管理所有界面字符串，不在代码中硬编码中文。

## 6. 结构化数据模型

### 6.1 核心实体

1. `Ingredient`：标准原料，含父类、多语言名称与别名、分类、`implicit_staple` 标记。
2. `Dish`：用户感知的一道菜，如“番茄炒蛋”。
3. `Recipe`：某道菜的一种具体做法，含份量、耗时、厨具占用、步骤、来源。
4. `RecipeRequirement`：做法与原料的关联，含角色、必要性、占用性、用量。
5. `SubstitutionRule`：全局默认替代规则。
6. `RecipeSubstitutionOverride`：菜谱级的替代覆盖（禁止或额外允许）。
7. `PantryTemplate`：调料柜模板。
8. `Source` / `ReviewRecord`：来源、许可、上游版本、审核记录。
9. 用户本地数据：`UserPantry`、`UserCurrentIngredients`、`UserMealBasket`、`UserSettings`。

### 6.2 关键字段

**RecipeRequirement**

| 字段 | 取值 | 说明 |
|---|---|---|
| `ingredient_id` | 原料 ID | 可指向类目级原料（如 `pork`） |
| `role` | `main` / `secondary` / `seasoning` / `garnish` | 用于展示分组，**不参与可制作性判定** |
| `importance` | `required` / `important` / `optional` | 参与判定，定义见下 |
| `consumes` | `true` / `false` | 是否为“占用型”原料，用于配餐冲突检测与“做了这道”扣减；通常主料为 true，调料为 false |
| `quantity` | `{value, unit}` 或 `{min, max, unit}` 或 `{unit: "to_taste"}` | 参考用量 |

**importance 定义**（必须在贡献指南中给出示例）：

- `required`：缺了做不成，或做出来已不是这道菜（如麻婆豆腐的豆腐、豆瓣酱）。
- `important`：缺了能做，但风味明显打折扣（如青椒炒肉的蚝油）。
- `optional`：可省略，影响轻微（如很多家常菜的鸡精、葱花点缀）。

**Recipe 新增字段**

| 字段 | 示例 | 用途 |
|---|---|---|
| `course` | `meat` / `veg` / `soup` / `staple` / `cold` | 荤菜、素菜、汤、主食、凉菜；用于配餐搭配与筛选 |
| `equipment_slots` | `[{"equipment": "wok", "minutes": 10}]` | 厨具占用与时长；用于厨具筛选与配餐并行判断 |
| `spicy_level` | `0`–`3` | 辣度筛选 |
| `time_minutes` | `15` | 总耗时（含准备） |

### 6.3 替代规则：两层结构 `[建议]`

**全局默认规则**：显式写出、带等级和风味说明。

| 等级 | 含义 | 结果分层影响 |
|---|---|---|
| `equivalent` | 几乎无差别 | 视为“有”，详情中注明 |
| `acceptable` | 可用，风味有变化 | 进入“能做·有提示”层 |
| `poor` | 勉强可用 | 默认不生效，仅在菜谱级覆盖中显式允许 |

**菜谱级覆盖**：只在例外处标注。

- `forbid`：本菜禁止某条全局规则（如某道菜必须用陈醋，米醋不可）。
- `allow`：本菜额外允许某个替代（包括 `poor` 级）。

这样仍符合“不凭借通用类别自动放宽必要条件”的原则：所有放宽都来自显式规则，只是不必在每道菜中重复书写。

## 7. 单菜匹配与排序引擎

### 7.1 输入与输出

**输入**：当次食材 ID 集合、调料柜 ID 集合、筛选条件（耗时、类别、厨具、辣度）。  
**输出**：按 `Dish` 聚合的结果列表，每项含选中的做法、所在层级、缺料列表、不确定项、使用的替代规则、推荐理由。

### 7.2 流水线

1. **归一化**：别名映射到标准 ID；合并当次食材、调料柜与隐含常备项为“可用集合”。
2. **候选召回**：通过原料→菜谱倒排索引，召回至少命中一项 `consumes: true` 原料的菜谱。
3. **逐项判定**：对每条需求，按以下顺序判定为“有 / 不确定 / 没有”：直接拥有或拥有其子类 → 有；存在可用替代规则 → 有（记录替代等级）；只拥有其父类 → 不确定；否则 → 没有。
4. **分层**：见 7.3。
5. **筛选**：应用用户选择的筛选标签。
6. **层内排序**：见 7.4。
7. **聚合**：同一 `Dish` 只保留最佳做法。
8. **解释生成**：基于判定记录生成简短理由。

### 7.3 分层定义 `[建议]`

| 层级 | 条件 | 界面呈现 |
|---|---|---|
| **能做** | `required` 和 `important` 全部为“有”，且未使用 `acceptable` 级替代 | 默认展示 |
| **能做·有提示** | `required` 全部为“有”或“不确定”；且存在以下至少一种情况：`important` 缺失、使用了 `acceptable` 替代、存在“不确定”项 | 默认展示，卡片上标注提示（如“缺蚝油，风味会打折扣”“请确认是否为里脊”） |
| **差一样** | 恰好 1 项 `required` 为“没有” | 折叠展示；同时用于“再买一样”统计 |
| 隐藏 | 2 项及以上 `required` 缺失 | 仅在前三层结果过少时作为兜底展示 |

`optional` 缺失不影响层级，仅在详情页显示。

[已确定] 未提供数量时，界面只声明“原料种类齐全”，不保证分量足够。

### 7.4 层内排序

按以下顺序比较，可解释、可回归测试：

1. 缺失 `important` 的数量（少者优先）。
2. “不确定”项数量（少者优先）。
3. **用掉手头食材的程度**：命中的 `consumes: true` 当次食材数量（多者优先），鼓励消耗现有食材。
4. 耗时（短者优先）。
5. 稳定的次级排序键（如 `dish_id`），保证结果确定。

v1 不引入个性化学习排序。后续若加入“收藏/常做”，只作为同分时的次级排序，不越过层级。

### 7.5 反向推荐：再买一样 `[建议]`

对“差一样”层的所有菜谱，按缺失的那一项原料聚合计数，展示前 3 项：

> 再买 **青椒**，能多做 6 道菜

点击后列出对应菜谱。该计算复用已有判定结果，无额外成本。

### 7.6 快捷筛选标签

结果页顶部的可点选标签（不需要进入设置）：

- 耗时：15 分钟内 / 30 分钟内
- 类别：荤菜 / 素菜 / 汤 / 主食
- 辣度：不辣
- 厨具：在设置中一次性声明“没有烤箱/蒸锅/空气炸锅”等，此后自动生效

### 7.7 边界条件

- 用户只选原料品种：只判断种类齐全，不保证分量。
- 菜谱步骤提及原料而用料表缺失：CI 告警，进入审核。
- 替代必须由显式规则支持。
- 没有任何可做菜谱：展示“差一样”层与“再买一样”提示。

### 7.8 复杂度

数据规模为数百道菜、数百种原料、数千条需求。启动时将数据加载为内存索引，每次输入变化重新计算全部候选的耗时在毫秒级，无需服务端。

## 8. 配餐：一顿饭（v1.5）

### 8.1 交互：菜篮渐进出现 `[已确定方向，细节为建议]`

- **默认不出现任何配餐界面**。只想找一道菜的用户不受影响。
- **手动组合**：每张菜卡有“加入这顿”按钮。菜篮非空时，底部出现横栏，例如：“这顿：番茄炒蛋 ＋ 还差一个荤菜、一个汤”。此时结果列表自动重排：主料已被占用的菜后移，能补齐搭配的菜前移。
- **自动配餐**：结果页顶部有“帮我配一顿”按钮，一键生成 2–3 套组合，每套可整体采用，也可替换其中一道。
- 两种方式共用同一个菜篮，可以先自动生成再手动调整。
- 菜篮完成后可进入“这顿饭”视图，依次查看各菜谱；v2 起提供制作顺序编排。

### 8.2 顿饭规模

- 在设置中一次性设置默认人数，配餐时可临时修改。
- 默认规则 `[建议]`：1–2 人为“一荤一素”或“一菜一汤”；3–4 人为“两菜一汤”或“三菜一汤”；5 人以上为“四菜一汤”。

### 8.3 主料冲突

- 默认保守：每种 `consumes: true` 原料只分配给一道菜。
- 冲突时提示“鸡蛋同时用于番茄炒蛋和蒸蛋”，提供“够用”按钮一键放行；放行仅对本次菜篮生效。
- 调料（`consumes: false`）不参与冲突检测。

### 8.4 自动配餐算法 `[建议]`

1. 从单菜引擎的“能做”与“能做·有提示”层中，按 `course` 各取排名前 15 的菜。
2. 按顿饭规模枚举组合（规模为数千量级，设备端可瞬时完成）。
3. 过滤：存在未放行的主料冲突的组合。
4. 分层评分，依次比较：
   1. 组合内各菜的层级（全部“能做”者优先）。
   2. 类别覆盖是否完整（如有荤有素有汤）。
   3. **厨具并行可行性**：根据 `equipment_slots` 估算最短完成时间，假设灶眼数量取自设置（默认 2）。
   4. 烹饪方式多样性（避免三道菜都是炒）。
   5. 用掉手头食材的总量。
5. 输出前 2–3 套组合，每套附一句解释，如“可并行完成，约 30 分钟；用掉 5 样你手头的食材”。

## 9. 界面与交互

### 9.1 页面结构

- **今日食材**（首页）：显示继承的上次选择；高频食材宫格（约 30 项）、分类、搜索（支持拼音首字母）；“清空”入口。
- **推荐结果**：可与首页合并为上下结构，选择变化时即时刷新；顶部为筛选标签与“帮我配一顿”；中部为分层结果；底部为“再买一样”提示与菜篮横栏。
- **菜谱详情**：用料表按“有 / 需确认 / 缺少 / 已替代”分组显示；步骤、耗时、份量；“做了这道”按钮；“报告问题”入口。
- **我的调料柜**：模板勾选与分类追加。
- **设置**：人数、灶眼数、厨具、备份、数据版本与网络行为说明；v2 起包含 BYOK 配置。

### 9.2 交互原则

- 以点击与勾选为主，尽量不需要打字。
- 老用户打开即见结果；新用户 60 秒内完成初始化。
- 每个推荐都可回答“为什么能做/为什么不能做”。
- 错误可以就地修正：在详情页直接修改“我有/我没有”，结果随之更新。
- 烹饪时的可用性（大字号、步骤逐条展示、屏幕常亮）列为 v1.5 候选改进。

### 9.3 视觉风格：Material Design 3 `[已确定]`

界面遵循 Google Material Design 3（Material You）设计语言，优先使用标准组件，不自造控件。

**组件映射** `[建议]`：

| 界面元素 | Material 3 组件 |
|---|---|
| 主导航 | Navigation bar（底部 3 个目的地：今天做什么 / 调料柜 / 设置） |
| 食材宫格与调料勾选 | Filter chip |
| 食材搜索 | Search bar（支持拼音首字母） |
| 快捷筛选标签 | Filter chip 横向滚动行 |
| 推荐结果 | List 或 Card；层级用分组标题区分 |
| 结果卡片上的提示（缺料、需确认） | Assist chip 或辅助文字，配图标 |
| “帮我配一顿” | Extended FAB |
| 菜篮 | 底部横栏 + Bottom sheet 展开详情 |
| “做了这道”扣减确认 | Bottom sheet 中的勾选列表 |
| 空状态与“再买一样” | Card |
| 操作反馈与撤销 | Snackbar（如“已移除 3 样食材 · 撤销”） |

**主题** `[已确定方向；具体色值为建议]`：

- **不使用动态取色**，所有设备使用固定的品牌配色。
- **浅色模式为黄白搭配**：页面和卡片以白色为主；**亮黄色只用于关键操作**，例如“帮我配一顿”Extended FAB、详情页的“做了这道”、首次设置的“完成”。其余按钮使用描边按钮或文字按钮。
- **选中状态**（已勾选的食材 chip、导航栏当前项指示器）使用很浅的奶黄底，起提示作用但不抢眼。
- 跟随系统深色/浅色模式切换。
- 字体使用系统默认字体，遵循 Material 3 字号层级；菜谱步骤页可单独放大。

**关于黄色的两个技术要点**：

1. **黄色按钮上的文字必须用深色**。白字在黄底上对比度远低于可读标准（约 1.6:1），因此关键按钮使用深棕色文字与图标。
2. **亮黄不能放在 `primary` 角色上**。Material 3 中 `primary` 也被用作白底上的文字色（文字按钮、链接）、复选框和开关的颜色，亮黄文字在白底上几乎看不清。用 Material Theme Builder 以黄色为种子直接生成配色时，浅色方案的 `primary` 会是偏暗的芥末色，也正是出于这个原因。做法是：
   - `primary` 用**深芥黄**，承担小面积强调（复选框、开关、文字按钮、链接），保证白底可读。
   - `primaryContainer` 用**柔和亮黄**，承担大面积填充（FAB、关键按钮）。
   - 在代码中封装一个统一的“关键按钮”组件（填充色 `primaryContainer`、文字色 `onPrimaryContainer`），各页面不单独写颜色。

**建议色值**（需在真机上目测并做对比度检查后定稿）：

| Material 3 色彩角色 | 浅色模式 | 深色模式 | 用途 |
|---|---|---|---|
| `primaryContainer` | `#FFD54F` 明亮暖黄 | `#D4B04A` | 关键按钮、FAB 填充 |
| `onPrimaryContainer` | `#3A2E00` | `#2A2100` | 关键按钮上的文字与图标 |
| `primary` | `#745B00` 深芥黄 | `#E8C65C` | 复选框、开关、文字按钮、链接 |
| `onPrimary` | `#FFFFFF` | `#3A2E00` | `primary` 填充上的文字 |
| `secondaryContainer` | `#FFF2C2` 浅奶黄 | `#3A3218` | 选中的 chip、导航指示器 |
| `onSecondaryContainer` | `#3A2E00` | `#FFF0C2` | 同上的文字 |
| `background` / `surface` | `#FFFFFF` | `#141412` | 页面、卡片 |
| `surfaceContainer` | `#F6F5F2` | `#1E1D1A` | 搜索栏、底部栏等分层背景 |
| `onSurface` | `#1C1B18` | `#E7E4DC` | 正文 |
| `onSurfaceVariant` | `#5F5D55` | `#C9C5BA` | 次要文字 |
| `outline` | `#D6D3CA` | `#4A4840` | 分隔线、描边按钮 |

**状态表达**：

- 黄色是品牌色，**只用于操作**，不用于表达警示。“能做·有提示”层使用中性色文字加信息图标，不用黄色或琥珀色，避免与关键按钮混淆，也避免与传统“警告黄”的含义冲突。
- 红色（`error`）只用于真正的错误。
- 层级状态（能做 / 有提示 / 差一样）不能只靠颜色区分，必须同时有图标或文字。

### 9.4 标志与 App 图标 `[已确定]`

**图形**：方向 C2「三点入锅」。一口深棕色的锅，上方三个由小到大的圆点落入锅中，代表“手头的食材 → 一道菜”，对应“以材选谱”。中间的圆点为白色描边圆，用来区分层次。

**几何**（108×108 自适应图标画布，所有图形位于中心半径 33 的安全区内）：

## 10. 数据集建设

### 10.1 数据源

**HowToCook（`Anduin2017/HowToCook`）**：

- 许可为 Unlicense `[需核实：正式导入前确认 LICENSE 文件与贡献内容的一致性，以及图片的来源]`。
- 规模约 370 篇，包括饮料、甜品、西式与东南亚/南亚菜式；去除这些后，中式家常菜估计约 250 道。
- 格式为 Markdown 自由文本，需要解析为结构化数据。
- 部分高频家常菜目前缺失（初步浏览目录未见青椒肉丝、酸菜鱼、干煸四季豆、京酱肉丝等），需要自行补充。
- 其衍生项目（如开源菜谱 API、“今天吃什么”类工具）可作为结构化成果的参考，使用前需逐项核验各自许可。

**自行编写与社区贡献**：通过开源仓库 PR 提交，按 CI 与审核流程合入，以项目数据许可发布。

**不使用**：未获授权的商业菜谱平台文字与图片。

### 10.2 高频家常菜清单 `[建议]`

在大规模导入之前，先建立一份约 200 道的**高频中式家常菜清单**，作为覆盖率指标的分母和数据建设的优先级依据。清单由维护者整理，并接受社区修订。

### 10.3 导入与治理流水线

`Raw（上游快照） → Parsed（自动解析） → Normalized（原料标准化） → Annotated（必要性/占用性/替代标注） → Reviewed（人工核验） → Published（打包发布）`

- 保留上游文件路径与 commit，不覆盖原始文本。
- 解析与标注阶段可由 LLM 离线生成**建议**，所有 `importance`、`consumes`、替代覆盖必须经人工审核后合入。
- 新别名与新原料进入词典审核。
- 去重：同名或高度相似的做法合并为同一 `Dish` 下的不同 `Recipe`。

**标注工作量估算**：300 道菜 × 平均 8 条需求 ≈ 2400 条需求标注。借助 LLM 预标注与两层替代结构，单人审核约需数十小时量级，可接受。

### 10.4 黄金测试集

人工标注的“厨房库存 → 期望结果”测试用例，覆盖：常见菜品、不同调料柜配置、别名、层级（具体/泛指）、不确定项、替代规则（含禁止覆盖）、配餐冲突。每个用例写明期望的层级与缺料列表。纳入 CI，每次数据或算法变更都运行。

## 11. 可选 BYOK 视觉识别（v2）

### 11.1 目标 `[已确定]`

用户自行配置视觉模型的 API Key，拍照识别食材以减少手动勾选。识别结果经用户确认后进入同一套匹配引擎。项目不承担任何模型费用。

### 11.2 流程

`拍照/选图 → 本地缩放并清除 EXIF → 请求预览与确认 → 设备直连服务商 → 解析结构化结果 → 用户确认/修正 → 标准原料映射 → 常规匹配`

- 仅发送图片与识别指令；调料柜、历史记录等不随请求发送。
- 模型输出须为结构化格式（原料名、可选数量估计、置信度），并校验其能映射到原料字典；无法映射的项交由用户选择或忽略。
- 未明确识别的对象不推定存在。

### 11.3 移动端实现要点 `[建议]`

- **设备直连服务商**，不经过任何项目方服务器。
- API Key 存储在 iOS Keychain / Android Keystore，不写入日志、备份文件或崩溃信息。
- **服务商适配**：优先实现 OpenAI 兼容协议适配器，可覆盖相当一部分服务商（含部分国内厂商）`[需核实：逐家确认视觉能力与兼容程度]`；其他协议按需增加独立适配器。
- 所有调用逻辑集中在一个独立模块中，便于源码审计。

### 11.4 可审查的调用机制 `[已确定的设计原则]`

- **发送前**：展示服务商、实际请求地址、模型、完整 Prompt 与参数、待发送图片（标明尺寸与编码方式）、费用预估（如可计算）。用户确认后才发送。
- **发送后**：本地调用日志，含时间、模型、脱敏请求、响应摘要、用量与费用（如服务商返回）。
- 用户可随时删除 Key 与清除日志；提供本地调用次数上限，并引导用户在服务商控制台设置预算。
- 界面声明必须与实际网络行为一致，并可通过源码核对。

## 12. 技术架构

### 12.1 总体结构 `[建议]`

```
┌─────────────────── Android App（Expo）─────────────────────┐
│  UI 层（i18n）                                              │
│  匹配引擎（纯函数，可独立测试）                              │
│  配餐引擎（v1.5）                                            │
│  本地存储：只读菜谱数据包（SQLite） + 用户数据（SQLite/KV）   │
│  BYOK 模块（v2，独立审计）                                   │
└─────────────────────────────────────────────────────────────┘
          │ v2 起，用户确认后直连          │ 后续版本（2.5）
          ▼                                ▼
   用户自选的模型服务商              社区菜谱分享服务（方案待定）
```

- **v1–v2 无业务后端**：没有账号、没有用户数据上传、没有服务器费用。社区分享（2.5）进入第二步时再设计服务端方案。
- **匹配在设备端完成**：引擎写成纯 TypeScript 函数，放在独立的 `/packages/engine` 中，与 UI 解耦。App 与数据 CI（Node.js）使用同一份引擎代码，黄金测试集在 CI 中跑的就是 App 里实际运行的逻辑。
- **数据包**：由 `/tools` 从 `/data` 构建，带数据版本号，打包进 APK。数据更新即发布新版本 APK。

### 12.2 跨平台框架

[已确定] 客户端使用 **Expo（React Native + TypeScript）**。v1 只发布 Android，保留将来支持 iOS 的可能。

**关键依赖** `[建议，引入前核对当前版本与维护状态]`：

| 用途 | 方案 | 说明 |
|---|---|---|
| Material 3 组件 | React Native Paper（v5 及以上） | 成熟、跨平台，默认即为 Material 3 主题 |
| 主题配色 | React Native Paper 自定义 MD3 主题 | 固定配色（见 9.3），不使用动态取色；用 Material Theme Builder 生成完整配色后，按 9.3 覆盖黄色相关角色 |
| 备选：原生 Material 3 组件 | Expo UI（`@expo/ui/jetpack-compose`） | 直接渲染 Jetpack Compose 原生组件，观感最接近原生；较新，且仅限 Android。可在个别页面试用，v1 不作为主方案 |
| 菜谱数据与用户数据 | `expo-sqlite` | 只读数据包 + 用户数据库 |
| 拼音索引 | 构建期生成 | 在 `/tools` 打包阶段预先计算，App 内不引入拼音转换库 |
| 国际化 | i18n 库（如 i18next） | 所有界面字符串外置 |
| BYOK 密钥存储（v2） | `expo-secure-store` | Android 上基于 Keystore 加密存储 |

依赖原则：每个依赖都要回答“是否必要”；不引入任何分析、广告、崩溃上报 SDK。

### 12.3 发布方式 `[已确定]`

- 源码托管在 GitHub；每个版本通过 GitHub Releases 提供 APK。
- 不上架应用商店，不针对任何地区的商店做专门适配。
- `[建议]` 使用 GitHub Actions 在打 tag 时自动构建并签名 APK，Release 页同时附上 SHA-256 校验值与变更说明（含数据版本变化）。
- `[建议]` 构建在 GitHub Actions 中本地完成（`npx expo prebuild` 后用 Gradle 构建 release APK），不依赖 EAS 云构建服务。这样任何人都能用公开的工作流复现构建过程。
- `[建议]` **权限清单白名单**：App 保留 `INTERNET` 权限。依赖库可能自动带入不需要的权限（例如 `expo-secure-store` 可能带入生物识别相关权限），用 `android.blockedPermissions` 移除。CI 中用 `aapt` 读取最终 APK 的权限清单，与仓库中维护的白名单比对，出现白名单外的权限即构建失败。
- `[建议]` 签名密钥长期固定、妥善备份。更换签名会导致用户无法覆盖安装、必须卸载重装，丢失本地数据。
- `[建议]` 保持 Release 命名与资产格式规范，方便用户用第三方工具追踪 GitHub Releases 自动更新。v1 应用内不做更新检查。

### 12.4 非功能性要求

- 推荐结果确定、可解释、可回归测试。
- 冷启动到显示结果 ≤ 1 秒（中端机型）。
- 全部核心功能离线可用。
- 用户数据仅存储在本地，提供导出与删除。
- 数据集具备来源记录、审核状态与版本号。

## 14. 风险与难点

1. **数据授权**：上游许可需逐项核实；图片与文字分别记录。
2. **中餐非标准化**：通过 Dish / Recipe 分层与多做法聚合缓解。
3. **可制作性误报**：直接损害信任。依靠黄金测试集、保守的替代规则与“不确定”状态缓解。
4. **标注主观性与成本**：`importance` 定义需配示例；两层替代结构降低重复标注。
5. **用户输入负担**：模板减法、隐含常备、继承上次、“做了这道”扣减共同缓解。
6. **开源维护负担**：数据审核是主要瓶颈；需清晰的贡献指南、CI 自动校验与小粒度 PR。
7. **APK 分发的门槛与信任**：用户需要允许安装未知来源应用，部分用户会有顾虑。依靠开源源码、固定签名、校验值、权限白名单与公开的网络行为清单（见 3.4）建立信任。
8. **国际化成本**：v1 只做结构准备，不做内容翻译，避免过早投入。
9. **BYOK 安全**：设备端密钥存储、请求预览的真实性、服务商协议差异。
10. **范围蔓延**：每项新功能都需回答“是否让用户更快找到真正能做的菜”。
11. **社区分享**：用户上传内容的质量参差，可能拉低推荐可信度；中心化服务带来服务器成本、内容审核、防滥用与法律责任。通过“社区/核验”分离、分步实现与上传时的许可确认缓解。

## 16. 给后续协作者（含 LLM）的分阶段工作指令

请以本文为产品需求的主要依据。每个阶段单独交付并评审，不要一次性完成全部阶段。不要自行加入 AI 生成菜谱、AI 排序、社交或账号功能。

**阶段 1：数据规范**
- 输出 Ingredient、Recipe、SubstitutionRule、PantryTemplate 的 JSON Schema。
- 编写贡献指南中的标注规范：`importance` 与 `consumes` 的判定方法与正反例、替代等级的判定方法。
- 产出 20 道菜的完整示例数据，覆盖层级、替代、禁止覆盖等情况。

**阶段 2：匹配引擎与黄金测试集**
- 在 `/packages/engine` 中以纯 TypeScript 函数实现第 7 节的单菜引擎（与 UI 无关），附单元测试。
- 建立至少 50 条黄金测试用例并接入 CI。

**阶段 3：数据导入**
- 编写 HowToCook 解析脚本，输出待审核的结构化草稿。
- 整理高频家常菜清单并给出覆盖率报告与缺口清单。

**阶段 4：v1 应用**
- 用 Expo + React Native Paper 完成第 9 节的页面（遵循 9.3 的 Material 3 规范）与第 4 节的用户数据行为；核心功能全部离线可用。
- 实现 9.3 的固定配色主题与统一的“关键按钮”组件。
- 配置 GitHub Actions：打 tag 自动构建签名 APK 并发布到 Releases。
- 按第 13 节的 v1 场景验收。

**阶段 5：v1.5 配餐**
- 实现第 8 节；补充配餐相关黄金测试用例。

**阶段 6：v2 BYOK 与本地菜谱**
- 实现第 11 节；提交独立的安全与网络行为审查说明。
- 实现本地私有菜谱编辑器与文件/二维码导入导出（2.5 第一步）。

**阶段 7：社区分享方案设计**
- 基于第一步的使用情况，比较中心化方案的成本、审核与隐私影响，给出建议，由维护者决策后再实现。

**评判方案的首要准则**：能否以最少交互、可靠数据和可解释算法，让用户快速找到真正能够制作的中式家常菜（或一顿饭），同时保持项目开源、核心功能离线、网络行为可审计，并控制维护成本。
